# Docker Setup on a NAS

This guide explains how to deploy **RBFA Calendar Sync** on a NAS using Docker Compose.

The setup consists of:

* `rbfa-calendar` — Flask web application
* `rbfa-calendar-updater` — automatically refreshes saved calendars
* A shared `data` directory
* Optional automatic Git backup of newly created calendars

Docker Compose is used to manage both containers together.

---

## 1. Prerequisites

Before starting, make sure your NAS supports:

* Docker
* Docker Compose
* SSH access or a terminal
* Git
* Internet access from the NAS

Check Docker:

```bash
docker --version
```

Check Docker Compose:

```bash
docker compose version
```

Docker recommends the current `docker compose` command rather than the old standalone `docker-compose` command.

If your NAS has a Docker GUI such as Synology Container Manager, you can still use the terminal commands in this guide through SSH.

---

# 2. Connect to the NAS

Connect to your NAS using SSH.

For example:

```bash
ssh <nas-user>@<nas-ip>
```

Replace:

```text
<nas-user>
```

with your NAS username and:

```text
<nas-ip>
```

with the IP address of your NAS.

Example:

```bash
ssh admin@192.168.1.100
```

---

# 3. Choose an application directory

Create a directory where the application will live.

For example:

```bash
mkdir -p /volume1/docker/rbfa-calendar
cd /volume1/docker/rbfa-calendar
```

The exact path depends on your NAS.

For a Synology NAS this could be:

```text
/volume1/docker/rbfa-calendar
```

For another NAS, use the directory where you normally store Docker application data.

From this point onward, this directory is referred to as:

```text
<APP_DIR>
```

---

# 4. Clone the GitHub repository

Clone the application into the directory.

```bash
git clone https://github.com/LienHoudenaert/rbfa_calendar_sync.git .
```

The repository is available here:

[RBFA Calendar Sync GitHub repository](https://github.com/LienHoudenaert/rbfa_calendar_sync?utm_source=chatgpt.com)

Check that the files are present:

```bash
ls
```

You should see files such as:

```text
Dockerfile
docker-compose.yml
app.py
config.py
requirements.txt
update_calendars.py
routes/
services/
templates/
static/
data/
```

---

# 5. Create the data directories

Create the persistent calendar directory:

```bash
mkdir -p data/ical
```

The application will use:

```text
data/
├── teams.json
└── ical/
    ├── <team-id>.ics
    └── ...
```

This directory is important.

It contains the calendars generated by the application and should survive Docker container updates and rebuilds.

---

# 6. Configure Git backup

The application can back up newly created calendars to GitHub.

The backup consists of:

```text
data/teams.json
data/ical/<team-id>.ics
```

The intended flow is:

```text
Create calendar
      ↓
Save team
      ↓
Generate .ics file
      ↓
Git add
      ↓
Git commit
      ↓
Git push
```

GitHub supports HTTPS Git operations using a personal access token instead of a password.

## 6.1 Create a GitHub token

Create a GitHub personal access token with permission to write to the repository.

For a fine-grained token, give it access to the repository and grant:

```text
Contents → Read and write
```

GitHub recommends fine-grained personal access tokens where possible.

**Do not put the token directly in Python source code or commit it to Git.**

---

# 7. Create the `.env` file

Inside the application directory:

```bash
nano .env
```

Add:

```env
GIT_REPO_URL=https://github.com/LienHoudenaert/rbfa_calendar_sync.git
GIT_BRANCH=main
GIT_USER_NAME=RBFA Calendar Sync
GIT_USER_EMAIL=calendar-sync@example.com
GITHUB_TOKEN=<your-github-token>
```

Replace:

```text
<your-github-token>
```

with the actual GitHub token.

For example:

```env
GITHUB_TOKEN=github_pat_xxxxxxxxxxxxxxxxx
```

Do **not** use the example token above.

---

# 8. Protect `.env`

Make sure `.env` is not committed to Git.

Check `.gitignore`:

```bash
cat .gitignore
```

It should contain:

```gitignore
.env
```

If it does not, add it:

```bash
echo ".env" >> .gitignore
```

Then verify:

```bash
git status
```

The `.env` file should not appear as an untracked file.

---

# 9. Configure Docker Compose

Edit the Compose configuration:

```bash
nano docker-compose.yml
```

Use the following structure:

```yaml
services:

  rbfa-calendar:
    build: .
    container_name: rbfa-calendar
    restart: unless-stopped

    ports:
      - "8080:8080"

    volumes:
      - ./data:/app/data

    environment:
      TZ: Europe/Brussels
      GIT_REPO_URL: ${GIT_REPO_URL}
      GIT_BRANCH: ${GIT_BRANCH:-main}
      GIT_USER_NAME: ${GIT_USER_NAME}
      GIT_USER_EMAIL: ${GIT_USER_EMAIL}
      GITHUB_TOKEN: ${GITHUB_TOKEN}

  rbfa-calendar-updater:
    build: .
    container_name: rbfa-calendar-updater
    restart: unless-stopped

    volumes:
      - ./data:/app/data

    environment:
      TZ: Europe/Brussels

    command: >
      sh -c "
      while true;
      do
        python update_calendars.py;
        sleep 21600;
      done
      "
```

The two containers share:

```yaml
- ./data:/app/data
```

Therefore both containers see the same:

```text
teams.json
```

and:

```text
ical/*.ics
```

---

# 10. Check the Compose configuration

Before starting anything, run:

```bash
docker compose config
```

This validates the Compose file and expands the variables from `.env`.

If there is a problem, fix it before continuing.

---

# 11. Build the Docker image

Build the application:

```bash
docker compose build
```

Or build and start everything in one command:

```bash
docker compose up -d --build
```

The first build can take a little longer because Python dependencies need to be installed.

---

# 12. Check the containers

Run:

```bash
docker compose ps
```

You should see something similar to:

```text
NAME                       STATUS
rbfa-calendar              Up
rbfa-calendar-updater      Up
```

If a container is not running, inspect its logs.

Web application:

```bash
docker compose logs rbfa-calendar
```

Updater:

```bash
docker compose logs rbfa-calendar-updater
```

To continuously follow the logs:

```bash
docker compose logs -f rbfa-calendar
```

or:

```bash
docker compose logs -f rbfa-calendar-updater
```

# 13. Open the application

The web container exposes port `8080`.

From another computer on your network, open:

```text
http://<nas-ip>:8080
```

For example:

```text
http://192.168.1.100:8080
```

The application should now be accessible.

# 14. Test calendar creation

Open the website and:

1. Search for your football club.
2. Select the club.
3. Select a team.
4. Create the calendar.
5. Copy the generated calendar URL.

After creating the calendar, check the NAS:

```bash
ls -la data
```

You should have:

```text
teams.json
```

Check the calendar directory:

```bash
ls -la data/ical
```

You should see something similar to:

```text
123456.ics
```

---

# 15. Test the Git backup

After creating a **new** calendar, check the Git repository:

```bash
git status
```

You should normally see the generated data committed already if the Git backup functionality is configured correctly.

Check the latest commit:

```bash
git log -1
```

You should see the new backup commit.

Then check GitHub to confirm that the changes have been pushed.

The expected files are:

```text
data/teams.json
data/ical/<team-id>.ics
```

---

# 16. Test the updater

The updater runs:

```bash
python update_calendars.py
```

every 6 hours.

The interval is controlled by:

```text
21600
```

seconds:

```text
21600 = 6 hours
```

You can manually test it without waiting six hours:

```bash
docker compose exec rbfa-calendar-updater python update_calendars.py
```

You should see output similar to:

```text
Found 3 saved teams.
Refreshing Club A - Team A (12345)
Successfully refreshed 12345
Refreshing Club B - Team B (67890)
Successfully refreshed 67890
```

---

# 17. Check the generated calendars

After running the updater:

```bash
ls -lh data/ical
```

The `.ics` files should have a recent modification time.

You can also inspect one:

```bash
head -20 data/ical/<team-id>.ics
```

You should see an iCalendar file beginning with something similar to:

```text
BEGIN:VCALENDAR
```

---

# 18. Make the application start automatically

Both containers use:

```yaml
restart: unless-stopped
```

Therefore Docker will restart them automatically after a NAS reboot, provided Docker itself starts automatically.

After rebooting the NAS, verify:

```bash
docker compose ps
```

You should again see both containers running.

---

# 19. Updating the application

When new code is pushed to GitHub, update the NAS with:

```bash
cd /volume1/docker/rbfa-calendar
git pull
```

Then rebuild and restart:

```bash
docker compose up -d --build
```

Check the status:

```bash
docker compose ps
```

The persistent `data/` directory is not deleted by rebuilding the containers.

---

# 20. Stopping the application

To stop both containers:

```bash
docker compose down
```

This stops and removes the containers but leaves:

```text
data/
```

on the NAS.

Start them again with:

```bash
docker compose up -d
```

---

# 21. Backing up the application data

The most important application data is:

```text
data/
├── teams.json
└── ical/
    └── *.ics
```

Keep a separate NAS backup of this directory as well.

The Git backup provides an additional remote copy, but it should not be your only backup.

# 22. Troubleshooting

## Container does not start

Run:

```bash
docker compose ps
```

Then:

```bash
docker compose logs rbfa-calendar
```

or:

```bash
docker compose logs rbfa-calendar-updater
```

---

## Port 8080 is already in use

Check which process is using the port:

```bash
sudo ss -ltnp | grep 8080
```

You can change the external port in `docker-compose.yml`.

For example:

```yaml
ports:
  - "5001:8080"
```

The application would then be available at:

```text
http://<nas-ip>:5001
```

The container itself continues to use port `8080`.

---

## Git backup fails

Check the web container logs:

```bash
docker compose logs rbfa-calendar
```

Verify that the environment variables are present:

```bash
docker compose config
```

Do not paste the resulting GitHub token into support requests or logs.

Also verify that the GitHub token has write permission to the repository.

GitHub's HTTPS authentication uses the personal access token as the credential for Git operations.

---

## Updater does not run

Check:

```bash
docker compose ps
```

Then:

```bash
docker compose logs rbfa-calendar-updater
```

Run it manually:

```bash
docker compose exec rbfa-calendar-updater python update_calendars.py
```

If the manual command works, the problem is likely with the container's periodic loop rather than the calendar generation itself.

# 24. Final NAS layout

After installation, the NAS should look approximately like this:

```text
/volume1/docker/rbfa-calendar/
│
├── .env
├── .git/
├── .gitignore
├── Dockerfile
├── docker-compose.yml
├── requirements.txt
├── app.py
├── update_calendars.py
│
├── routes/
├── services/
├── static/
├── templates/
├── translations/
├── utils/
│
└── data/
    ├── teams.json
    └── ical/
        ├── <team-id>.ics
        ├── <team-id>.ics
        └── ...
```

The `.env` file contains the GitHub credentials and must remain private.

The `data/` directory contains the persistent calendar data.

The `.git/` directory is required if the application itself is performing Git commits and pushes.

# 25. Quick installation checklist

Use this checklist when installing on a new NAS:

* [ ] Docker installed
* [ ] Docker Compose available
* [ ] SSH access working
* [ ] Application directory created
* [ ] Repository cloned
* [ ] `data/ical` created
* [ ] GitHub token created
* [ ] `.env` created
* [ ] `.env` added to `.gitignore`
* [ ] `docker-compose.yml` configured
* [ ] `docker compose config` succeeds
* [ ] Docker images built
* [ ] Web container running
* [ ] Updater container running
* [ ] Website accessible on port `8080`
* [ ] Test calendar created
* [ ] `.ics` file generated
* [ ] Git backup tested
* [ ] Updater tested manually
* [ ] NAS restart tested
* [ ] `data/` included in NAS backups

Once these steps are complete, the RBFA Calendar Sync service should run continuously on the NAS, with the web application serving calendars and the updater refreshing them automatically every six hours.
